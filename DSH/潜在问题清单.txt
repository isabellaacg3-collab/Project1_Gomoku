A1. 悬空的全局声明：playerTurn
    位置：Gomoku.h:16
    现象：extern bool playerTurn; 只有声明，整个工程没有任何定义与使用。
    后果：虽不会导致链接失败（因为没人引用），但属于死声明，
          会误导读代码的人以为有"玩家回合"这个状态。
    建议：直接删掉这一行。
    备注：本次交付的 ai_normal.cpp / ai_hard.cpp 都是独立自用棋盘，
          没有引用它，删除不会影响任何已实现的 AI。

A2. 未使用的全局计数器
    位置：DSH/ai_hard.cpp 搜索统计区
    现象：曾有一个 g_rootMoves 计数变量被声明但从未使用，编译时
          -Wall -Wextra 会报 unused-variable 警告。
    状态：**已修复**（我在交付前把该变量删掉了，并保留了两个真正
          用得上的统计量 g_nodes / g_cutoffs）。此处列出是提醒你：
          如果后续自己加统计量，记得同步清理未使用的声明。
    建议：保持"零警告"编译，任何新加的统计变量都要么用上、要么删掉。

A3. 菜单标题位置不对称
    位置：StartMenu.cpp:9   xyprintf(360,120,"GOMOKU");
    现象：菜单按钮画在 x = 280~520（中心 400），标题却从 360 起画，
          按默认字体宽度估算，标题中心约在 400 偏右一点，视觉上不正。
    后果：纯外观问题。
    建议：把起点改成 370 左右并实测一次；或改用居中对齐的文本输出
          函数（EGE 有 settextjustify / 类似接口）来真正居中。

A4. 难度面板没有清屏标题以外的内容
    位置：AI.cpp:5  drawDiffPanel()
    现象：函数里只 cleardevice() + setcolor(BLACK) + 画三个按钮，
          没有重置背景色、字体等其它绘图状态。
    后果：当前调用路径下不会出问题（主循环里没有改过这些状态），
          但属于"依赖外部状态"的脆弱写法。
    建议：在 cleardevice() 后补一句 setbkcolor(EGERGB(238,196,126))，
          与 main() 里设置的背景色保持一致，避免以后状态被改坏。

A5. 版本库卫生
    位置：工作区根目录
    现象：Gomoku.h.gch（1.1MB 预编译头，时间戳早于 Gomoku.h）、
          *.o、Project1_Gomoku.exe、Project1_Gomoku.layout 都留在目录里。
          .gitignore 已忽略这些，但它们仍存在于工作区。
    后果：不影响运行。唯一的真实风险是——改了 Gomoku.h 之后如果
          gch 没被重建，Dev-C++ 可能沿用旧的预编译头，让人误以为
          "改了代码却没生效"。
    建议：动过 Gomoku.h 之后，在 Dev-C++ 里执行一次"全部重新编译"；
          平时不必删。

A6. 源码没有注释
    位置：工程原有全部源码
    现象：按课件要求"源码取消所有的注释"，原有代码确实零注释。
    后果：不算 bug，但评分时"可读性/讲解"可能吃亏。
    建议：保留一份带注释的副本用于答辩讲解（DSH 里两个 AI 文件已经
          是逐段中文注释的写法，可以直接作为示例）。

 B 类：健壮性隐患与体验问题
------------------------------------------------------------------------

B1. countMultiple 数组存在越界读的隐患
    位置：AI.cpp:76（getScore 的返回语句）、AI.h:2（countMultiple 定义）
    现象：countMultiple[11] 在 AI.h 里只声明了 11 个元素
          （下标 0~10）。而 getScore() 的 count 由两段各最多 times(4) 次
          的累计、再加两次 count++ 组成，理论上可以取到 11，
          直接索引 countMultiple[11] 就越界了。
          更直接的问题是：代码没有对 count 做任何上限判断。
    后果：越界读属于未定义行为。实际对局中极难凑出触发条件，
          但一旦发生可能读到垃圾分值，AI 行为会变得莫名其妙。
    建议：改用"取值前夹一下"的写法，例如：
              if(count > 10){ count = 10; }
          或者把数组扩到 16 个元素并留好注释。**推荐前者**，
          改动一行、风险最低。

B2. 数组下标未做合法性校验
    位置：AI.cpp:28-29（getScore 内 board[rowptr][colptr] 的访问）
    现象：该函数通过调用方传入的 row/col 与方向增量计算下标，
          循环里只判断了"是否越出棋盘边界"，
          但没有校验入参 row/col 本身是否合法。
    后果：当前的调用路径（chooseEasyMove 只传 0~14）是安全的，
          属于"防御性编程缺失"。如果以后有其它代码复用 getScore
          并传入了非法坐标，就会越界访问 board。
    建议：在函数开头加一句边界断言式判断：
              if(row < 0 || row >= lines || col < 0 || col >= lines){ return 0; }
          或者在 chooseEasyMove 调用处保证坐标范围，并写注释说明这个约定。

B3. chooseEasyMove 的初值语义容易让人误判
    位置：AI.cpp:80（int bestScore = 0;）与 AI.cpp:87（> 比较）
    现象：bestScore 初值为 0 且用严格大于比较。在"所有候选点都得 0 分"
          的局面（例如空盘附近只有孤子）下，bestRow/bestCol 可能一直
          没有被赋值。
    后果：目前因为 chooseEasyMove 只遍历"空点"，且返回值只在
          放在后面判断，所以不会真正崩溃；但这个初值选择是
          一个经典陷阱（一旦以后改成遍历全部格子或引入负分，就会崩）。
    建议：把初值改成 -1，并在函数开头加一句"棋盘全空则直接返回天元"，
          既修掉隐患，也让简单 AI 的开局从"左上角第一格"变得合理。

B4. 局域网按钮点了没有反应
    位置：StartMenu.cpp:18（画 "LAN(coming soon)"）与 main.cpp:43-52
          （MENU 状态的点击分支只处理了 LOCAL 和 AI 两个框）
    现象：菜单上明明画了第三个框，但点击它没有任何响应，
          主循环里也没有 LAN_GAME 的分支。
    后果：不算崩溃，但演示时点它没反应，观感上像是坏掉了。
    建议：二选一——
          (a) 短期：把该框改成灰色/不可用样式，或直接不画，
              避免"画了却点不动"的误导；
          (b) 长期：接上真正的联机模式（思路见
              DSH/局域网联机说明.txt）。

B5. AI 落子没有缓冲，玩家看不到对手"思考"的过程
    位置：main.cpp:31-40（主循环开头就是 AI 走子）
    现象：玩家落子后立刻 switchPlayer，同一帧或下一帧 AI 的判断
          就成立并马上落子，中间的延迟只有 1 帧（约 16 毫秒）。
    后果：体验上像是"你刚点完，对手的棋子瞬间就出现了"，
          缺少节奏感，也不容易看清对手下了哪里。
    建议：加一个"起手延迟"，例如记录 AI 回合开始的帧计数，
          累计到 20~30 帧（约 0.3~0.5 秒）后再让 AI 落子。
          注意不要在 AI 分支里用阻塞式 delay，那会卡住鼠标与画面。

B6. 胜场数文字贴近窗口右边界
    位置：Gomoku.cpp:10-11   xyprintf(650, 60/90, "White Wins: %d", ...)
    现象：文字从 x=650 起画，窗口宽 800。当前字体下文字宽度大约
          在 100 像素上下，勉强放得下；一旦换更大的字体、
          或把 winLimit 调大让数字变宽，就可能被裁掉。
    后果：纯显示问题。
    建议：起点左移一些（例如 620），或把这段统计文字挪到棋盘下方的
          空白区域，给右侧留足余量。


------------------------------------------------------------------------
 C 类：功能缺陷与玩法层面的问题（严重性最高）
------------------------------------------------------------------------

C1. 回合提示在多种情况下显示错误
    位置：Gomoku.cpp:12（drawBoard 里写死 "White Turn"）、
          Gomoku.cpp:111-115（checkWin 未获胜时才更新回合文字）
    现象：回合文字只在"checkWin 判定未获胜"这一个分支里更新。

        （1）resetRound() / resetGame() 都会调用 drawBoard()，
            而 drawBoard 无条件画 "White Turn"。但这两个函数
            同时把 currentPlayer 置为 1（黑），于是**新一轮开始时，
            明明轮到黑方，界面却写着 White Turn**。
            注意：本工程的约定是 1=白、2=黑（见 Gomoku.h 与
            main.cpp 中 currentPlayer == 2 才是 AI 黑方），
            所以这里确实是写错了。
        （2）游戏结束时，回合文字停在上一手的状态，没有被清除，
            与 "White Win!" / "Black Win!" 同时显示，自相矛盾。
        （3）AI_GAME_EASY 分支直接进入对局时同样沿用写死的文字。

    后果：玩家看到的"轮到谁"经常是错的，尤其在每局开局那一步，
          很容易让人以为程序卡住了或规则不对。
    建议：把回合文字的绘制**统一收口**，例如新增一个
              void drawTurnText(int currentPlayer);
          在里面根据 currentPlayer 输出 "White Turn" / "Black Turn"，
          然后让 drawBoard、switchPlayer 之后、resetRound/resetGame
          都调用它。核心要点是：不要把回合信息写死在 drawBoard 里。

C2. "Next Round" 按钮的标签会被回合文字覆盖
    位置：Gomoku.cpp:97（roundWin 画 "Next Round" 于 670,240）
          与 Gomoku.cpp:112/114（checkWin 画回合文字于 650,320）
    现象：当**人类玩家**下出制胜一手时，调用顺序是
              placeChess -> checkWin -> roundWin（画 Next Round 按钮）
                        -> 回到 checkWin 继续执行
                        -> 又把回合文字画到 (650,320)
          两块文字的矩形区域有重叠（按钮框是 650~780 / 220~270，
          回合文字基线在 y=320，实际像素范围会向上覆盖到按钮下沿），
          于是按钮标签被盖花、变得难以阅读。

    重要说明（我实测确认过）：EGE 的文字背景默认是 TRANSPARENT。
          我用一个离屏实验验证过：在纯白矩形上输出文字后，
          矩形内部的白色像素仍然保留（1535 个底色像素 + 129 个字形像素），
          说明文字**不会**把下面的内容涂掉，只是叠加上去。
          因此这里**不会**导致按钮消失或游戏卡死——按钮的方框
          和点击响应都还在，只是标签被两条文字叠在一起、看着糊。
          所以它的严重性是"显示缺陷"，而不是"流程卡死"。

    后果：每当玩家获胜时，续局按钮的标签都是糊的，玩家容易
          找不到该点哪里（功能仍在，但可发现性差）。
    建议：两种改法任选——
          (a) 最省事：把回合文字与按钮错开位置，例如把回合提示
              挪到 (650, 350) 或按钮框之外的空位；
          (b) 更彻底：按 C1 的建议把回合文字收口到一处，
              并在"本局已结束"时**不要再画回合文字**
              （在 roundWin 之后直接 return，不再走画回合文字那条分支）。

C3. 棋盘下满后游戏僵死（无平局判定）
    位置：main.cpp:60-67（LOCAL 分支）、main.cpp:104-121（AI 分支）
    现象：全项目没有任何"棋盘已满"的判断。一旦 225 个交叉点下完
          且无人五连，canPlaceChess 之后永远返回 false，
          此时：
            - 点棋盘没有任何反应；
            - roundOver / gameOver 都还是 false，
              所以"下一局 / 重开"的分支也不会进入。
          结果就是这一局彻底卡死，只能点 "Back to Menu" 硬退。
    后果：这是**功能性缺陷**。棋盘下满且无五连虽然罕见，
          但并非不可能（尤其在 AI 只会下左上角、棋力很弱的情况下，
          双方互不干扰地铺满棋盘是可以发生的）。
    建议：新增一个"满盘即和棋"的判定：扫描棋盘确认没有空位后，
          置 gameOver = true 并画出和棋提示与"Reset Game"按钮。
          具体代码之前已经给过一份（用 /* */ 关闭的形式，
          按你的要求未启用），可以直接拿来打开。
          另外建议一并处理 chooseEasyMove 返回 false 的情况
          （AI 无法落子时不要既不落子也不换手）。

C4. 人机对战中人类固定执白先手，且无法选择先手
    位置：main.cpp:30（currentPlayer 初值 1）、
          main.cpp:32（AI 走子条件是 currentPlayer == 2）、
          main.cpp:104（人类走子条件是 currentPlayer == 1）
    现象：本工程的约定是 1=白、2=黑。currentPlayer 初值恒为 1，
          于是**人类执白、并且永远先手**，AI 执黑后手；
          界面与代码里也没有任何"交换先手 / 我执黑"的开关。
    后果：不算程序错误，但有两个现实影响：
          (1) 五子棋先手优势明显，固定先手让对局单调；
          (2) 演示时人类先走、AI 后应，如果想让 AI 先手亮一手棋，
              目前做不到。
    建议：在难度面板上加一个"先手 / 后手"选择（或开局随机），
          并把 currentPlayer 的初值改为按选择结果设置；
          若要支持"人类执黑"，还需把 main.cpp 里
          `currentPlayer == 1` / `== 2` 这两处判断改成
          "是否轮到人类"的语义（例如用一个 bool isHumanTurn 标志），
          而不是写死具体颜色值。**推荐后者**，因为写死颜色是
          这个分支一系列脆弱点的根源。

C5. LOCAL 与 AI 两个分支是复制粘贴，维护性差
    位置：main.cpp:53-86（LOCAL_GAME）与 main.cpp:107-141（AI_GAME_EASY）
    现象：两个分支是一大段几乎相同的代码（落子判断、checkWin、
          switchPlayer、下一局/重开按钮），只在"落子条件"与
          "进入方式"上不同：LOCAL 是 `!roundOver && !gameOver`，
          AI 是 `!roundOver && !gameOver && currentPlayer == 1`。

    说明（这一点我实际核对过，避免误判）：这两个分支对
          "下一局 / 重开"的处理**行为是一致的**——因为那两条
          else-if 是挂在**内层 if** 上的，当第一个条件因
          currentPlayer == 2 而不成立时，else-if 链仍会被求值，
          所以结束态按钮在 AI 模式下同样可点。
          也就是说：AI 模式**不存在**"AI 获胜后点不动重开按钮"的问题。

    后果：真正的代价是维护性——同一段逻辑存在两份，以后每加一个
          模式（例如联机）都要再抄一遍，改一处容易漏另一处。
          本轮排查中我一度据此误判出不存在的 bug，正好说明这种
          重复代码会让人（和工具）读错控制流。
    建议：把公共部分抽成函数，例如
              void handlePlaceChess(int msgX, int msgY, int &currentPlayer);
              void handleRoundEndButtons(int msgX, int msgY, int &currentPlayer);
          LOCAL 与 AI 分支只保留"该不该轮到谁落子"的判断，
          然后都调用这两个函数。

 修复优先级建议
------------------------------------------------------------------------

  第一优先（影响正常游玩，建议先做）：
      C3  满盘僵死      —— 加平局判定；顺带处理 chooseEasyMove 返回
                           false 时"不落子也不换手"的分支
      C1  回合提示错误  —— 把回合文字收口到一处统一绘制
      C2  按钮标签被盖  —— 挪开回合文字位置，或本局结束后不再画它

  第二优先（改动都很小，收益明显）：
      B3  bestScore 初值改 -1 + 空盘走天元（顺带让简单 AI 不那么呆）
      B1  count 取值前夹一下上限（一行）
      B5  AI 落子加 0.3 秒左右延迟，让玩家看清对手落子
      B4  LAN 按钮：要么置灰、要么接上联机
      C4  增加先手/后手选择，并把"轮到谁"从颜色值改为语义标志

  第三优先（整洁性，不影响演示）：
      C5  消除两个分支的重复代码
      A1/A3/A4/A5/A6  死声明、标题位置、背景色、构建产物、注释

  一句提醒：C5 虽然是"整洁性"问题，但它是 C1~C4 反复出现的土壤。
        上述 C2 的补法（本局结束后直接 return）会改变控制流，
        如果两处副本没有同步修改，就会出现真正的不一致。
        因此建议在做完第一优先后，顺手把 C5 重构掉。

 附：本清单中经过实际验证的两条结论
------------------------------------------------------------------------

  1. EGE 文字背景默认是 TRANSPARENT（不是 OPAQUE）。
     验证方式：写了一个离屏小程序，在纯白矩形上用蓝色输出文字，
     再用 getHDC() + GetPixel 统计像素——白底像素保留了 1535 个、
     字形像素 129 个，说明文字只叠加、不会把下面的内容涂掉。
     意义：C2 因此只是"标签糊了"，**不会**导致按钮消失或流程卡死，
           严重性按显示缺陷处理，而不是按卡死处理。
           如果你实测发现按钮真的没了，那说明我这条结论有误，
           请告诉我，我会重新排查。

  2. AI 分支的结束态按钮是**可点**的（不存在"AI 获胜后卡住"）。
     验证方式：按 C++ 的 else-if 绑定规则复刻该分支，
     对 currentPlayer = 1 / 2 × {对局中, 本局结束, 对局结束}
     六种组合逐一求值，结束态两种情况下都进入了对应分支。
     意义：我把最初误判的那条 bug 从清单里删掉了。
